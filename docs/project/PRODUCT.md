# Цель продукта и рабочий MVP

**Статус документа:** Целевое состояние

**Проверено относительно:** `main` @ `cfc06ec`
**Дата содержательной проверки:** 2026-08-11

## Проблема

Локальный Docker на Mac может занимать значительную долю памяти, CPU и диска. При этом у пользователя может быть отдельный Windows-компьютер в той же частной сети, ресурсы которого удобнее использовать для контейнеров.

Remote Docker должен перенести только Docker-нагрузку на Windows, не превращая Windows в удалённый рабочий стол и не перенося туда редактор, Git, shell, исходный код как единственную копию или обычные инструменты разработки.

## Основной пользовательский сценарий

1. Пользователь вручную запускает приложение на Mac и Windows.
2. Windows явно начинает ожидать подключение, а Mac явно запускает поиск.
3. Mac выбирает ожидаемый Windows-компьютер.
4. Оба устройства показывают участников и одинаковый шестизначный код.
5. Пользователь подтверждает запрос на Windows.
6. Mac регистрирует папки проектов, которые нужны Docker bind mounts.
7. Обычные команды `docker` и `docker compose` с Mac выполняются на Windows Docker Engine.
8. Опубликованные поддерживаемые TCP-порты доступны на Mac через `localhost`.
9. Оба приложения показывают актуальное состояние соединения и свою роль.
10. Pause, Disconnect, Forget и Finish work дают понятный и наблюдаемый результат.

## Определение рабочего MVP

MVP считается рабочим, когда выполнены все условия:

- роли фиксированы: Mac — клиент, Windows — Docker-хост;
- поддерживается одна доверенная пара Mac↔Windows;
- установка и запуск выполняются вручную, без autostart;
- discovery, pairing, сравнение кода, approve, reject и cancel работают через UI;
- поддерживаются произвольные обычные Docker/Compose операции, а не одна заранее заданная команда;
- выбранные Mac workspaces синхронизируются в Linux filesystem управляемого WSL2;
- images, containers, named volumes, databases, writable layers и build cache остаются на Windows;
- статические TCP publications доступны через те же свободные порты Mac `localhost`;
- оба UI получают актуальные состояния и не показывают устаревшую связь как активную;
- завершение приложения останавливает принадлежащие Remote Docker процессы, relays, synchronization и управляемую workload;
- update и uninstall не повреждают чужие файлы, Docker contexts, firewall rules, WSL distributions и Docker data;
- Docker API не доступен в LAN как незащищённый TCP endpoint;
- ошибки показываются пользователю и не маскируются пустыми уведомлениями;
- CPU/RAM и контейнерные метрики относятся к правильному устройству либо явно недоступны.

## Критерии успеха

- Пользователь выполняет стандартный Docker workflow с Mac без запуска локального Docker Engine.
- Основная CPU/RAM/Disk нагрузка Docker наблюдается на Windows.
- Временная потеря Wi-Fi не требует повторного pairing, если доверие не было удалено.
- После Finish work нет принадлежащих приложению фоновых процессов и автоматического повторного запуска.
- Чистая установка, обновление и удаление имеют понятный результат и не требуют ручного редактирования системных файлов.
- Все обязательные строки [матрицы проверки](VERIFICATION.md) имеют доказанный успешный результат для релизного artifact.

## Что означает стабильность

Стабильность — это не отсутствие любой теоретической гонки. Для MVP она означает:

- основной сценарий воспроизводимо работает на реальных устройствах;
- подтверждённые P0/P1 закрыты;
- ошибки сети и ОС ограничены по времени и приводят к понятному состоянию;
- cleanup идемпотентен и не изменяет чужие ресурсы;
- длительная работа не показывает неограниченный рост памяти, процессов, соединений или файлов;
- обновление между поддерживаемыми версиями не оставляет одновременно работающие несовместимые процессы;
- невыполненные или редкие проверки честно остаются в backlog.

## Границы первой версии

- одна частная Wi-Fi или Ethernet сеть;
- один Mac и один Windows host;
- Linux containers в managed WSL2;
- TCP port forwarding;
- source workspaces ниже разрешённой Mac root;
- ручной startup на обеих платформах;
- бесплатные unsigned packages с проверяемыми checksums и manifest.

## Явные не-цели

- Kubernetes и multi-host cluster;
- Windows containers;
- доступ через публичный интернет;
- общий доступ нескольких Mac к одному host;
- UDP forwarding и host networking;
- перенос редактора, Git, shell и всех тестов на Windows;
- Docker Desktop GUI на Mac;
- автоматическое исправление чужих Docker contexts, firewall rules или процессов;
- абсолютная атомарность относительно произвольной внешней команды Docker CLI, если Docker сам не предоставляет условную операцию.
